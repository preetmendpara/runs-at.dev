# DNS infrastructure

Status as of 2026-11-13: production DNS is **Cloudflare**. The PowerDNS stack described below has been written but **not provisioned, and it is not in service**.

## Today (production)

- Authoritative: `aida.ns.cloudflare.com`, `damon.ns.cloudflare.com` (SOA serial 2419899443 at audit time).
- Registrar: **Cloudflare Registrar**, which does not allow custom nameservers.
- DNSSEC: the zone is signed at Cloudflare, but there is no DS record at the registry, so the delegation is unsigned.
- Source of truth for claims: the Git registry (`domains/*.json`, `owners/*.json`, `entitlements/*.json`). The app (Next.js on Vercel, GitHub OAuth) writes claims through the GitHub contents API.
- Publishing: a push to `main` that touches `domains/` runs `.github/workflows/sync-dns.yml`, which runs `scripts/sync-dns.mjs` and writes the records to Cloudflare (TTL 300).
- Records that are not in the registry:
  - apex A records (Vercel)
  - apex MX and SPF (Cloudflare Email Routing)
  - apex TXT
  - the `www` CNAME to Vercel
  - the `_vercel` TXT
  - the proxied wildcard, answered by `cloudflare/worker.js` (the profile card)

  A snapshot of all of these is in `migration/backup/live-dns-export.json`.
- `URL` records are redirects done by the app and create no DNS record. The wildcard answers those names and the app does the redirect.

Known production problem: the zone is at Cloudflare's record limit, so `sync-dns` fails with `Record quota exceeded`, and 16 declared records are not live. See [troubleshooting](../operations/troubleshooting.md).

## Planned (PowerDNS on Oracle Cloud Always Free)

```
Git registry --push--> sync-dns.mjs (DNS_PROVIDER=powerdns)
                          | HTTP API on 127.0.0.1:8081 on ns1 (reached through an SSH tunnel)
                          v
   ns1 (primary, PostgreSQL on loopback) --NOTIFY + TSIG AXFR over VCN--> ns2 (secondary, SQLite)
     10.53.1.11 + reserved public IP                                   10.53.1.12 + reserved public IP
```

`sync-dns.mjs` defaults to `DNS_PROVIDER=cloudflare`. With `DNS_PROVIDER=powerdns` it also needs `PDNS_PRIMARY_IP` and `PDNS_SECONDARY_IPS`, and `PDNS_DRY_RUN=1` only builds the plan. In this mode it refuses any plan that deletes more than 25 RRsets. So far it has been tested only against fake HTTP responses and an in-memory provider, never a real PowerDNS server.

Schema: `lib/schema.js` is unchanged.
- CAA and SRV are validated only in the PowerDNS layer, because Cloudflare's flat `content` request body cannot publish them.
- NS records in claims are rejected everywhere.

## Limits of the planned design

- **No redundancy across providers.** ns1 and ns2 are two VMs in one OCI tenancy, one region and one VCN. An account suspension, a billing or limits problem, a regional outage, or a mistake in that account takes both down. Real redundancy needs a secondary at a different provider, added as a third NS. Any DNS service that accepts TSIG-signed AXFR from ns1 will do.
- **Always Free idle reclamation.** Oracle may reclaim Always Free compute instances it considers idle, judged by low CPU, network and memory use over a 7-day window under Oracle's published policy (check the current terms). An authoritative DNS server carries very little load, so this is a real risk. Ways to reduce it:
  - Monitor both instances from outside OCI.
  - Keep the zone export and backups off the instances.
  - Consider upgrading the tenancy to Pay As You Go: Always Free resources stay free but are no longer reclaimed as idle.
  - Keep the Cloudflare zone available for [rollback](../operations/rollback.md).
- The wildcard and apex mail depend on Cloudflare today (the Worker and Email Routing). Both need replacements before cutover.
- DNSSEC is not configured on PowerDNS.
- Both hosts use the same automatic-reboot time. Stagger it.
